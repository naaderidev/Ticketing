# بازسازی داده نمایشی مطابق سند محصول

فرمان `npm run db:bootstrap-demo` دیتابیس نسخه نمایشی را از روی Prisma schema بازسازی
می‌کند. تمام داده‌ها و کاربران قبلی را حذف می‌کند و دقیقاً ۱۲ حساب ارائه با نقش‌های
سیستمی، مدیریتی، کارشناسی، سازمانی و مشتری را از منبع مشترک
`src/config/demo-accounts.json` می‌سازد. نشست‌های ورود عمداً حذف می‌شوند؛ بنابراین پس از
اجرا باید دوباره وارد شد.

اسکریپت فقط در شرایط زیر اجرا می‌شود:

- `DEMO_MODE=true` باشد؛
- `ALLOW_DEMO_DATABASE_RESET=true` باشد؛
- میزبان محلی یا عضو `DEMO_DATABASE_HOST_ALLOWLIST` باشد؛
- برای میزبان غیرمحلی نام دیتابیس با `DEMO_DATABASE_RESET_NAME` دقیقاً برابر باشد؛
- عبارت تأیید دقیق `RESET_DEMO_DATABASE` ارسال شود.

```powershell
npm run db:bootstrap-demo
```

داده بازسازی‌شده شامل Party و پروفایل ۱۲ کاربر دمو، یک سازمان نمونه و محدوده‌های دسترسی،
هشت سرویس، یازده نوع درخواست، نه تیم، یازده صف، مسیرهای نسخه‌دار، چهار سیاست SLA، پایگاه دانش،
پاسخ‌های آماده و ۵۵ درخواست نمونه در وضعیت‌های اصلی چرخه عمر است.

برای ارائه داشبورد مدیریتی، Seed علاوه بر داده عملیاتی موارد زیر را به‌شکل سازگار و قابل تکرار
می‌سازد:

- Fact سالم برای تمام درخواست‌های نمونه و Checkpoint همگام با Outbox؛
- نمونه‌های زمان پاسخ و حل، SLA رعایت‌شده و نقض‌شده؛
- FCR موفق و ناموفق، بازگشایی و حداقل ۳۰ امتیاز برای عبور از آستانه انتشار CSAT؛
- Journeyهای حل خودکار، تبدیل به تیکت و ورود کارشناس؛
- ۱۰۰ روز حجم تراکنش `VERIFIED` برای تمام انواع قابل انتخاب در داشبورد، در Scope سراسری و سازمانی؛
- یک خوشه پرتکرار قابل Drill-down با حداقل پنج تیکت و سه مشتری متمایز.

پس از Seed، پوشش بازه پیش‌فرض ۳۰روزه را می‌توان با فرمان زیر کنترل کرد:

```powershell
npm run verify:reporting-demo-data
```

صحت ۱۲ حساب، رمزهای عبور، نقش‌ها، تخصیص تیکت به همه مشتریان و پوشش وضعیت‌های چرخه عمر
نیز با فرمان زیر قابل کنترل است:

```powershell
npm run verify:demo-accounts
```

برای اینکه حساب‌های مدیر موجود بتوانند سناریوی فضای کاری را بدون نقض قاعده مالکیت اجرا کنند،
هر مدیر در داده نمایشی با نقش `SUPPORT_AGENT` عضو فعال تمام تیم‌های Seedشده می‌شود. نقش سراسری
مدیر جای عضویت تیمی مالک را نمی‌گیرد و سرویس تخصیص همچنان مالک خارج از تیم را رد می‌کند.
هر دو حساب مدیر نیز Assignmentهای صریح و مستقل `SUPPORT_MANAGER/GLOBAL` و
`REPORTING_EXPORTER/GLOBAL` می‌گیرند تا گزارش مدیریتی KPI و خروجی CSV با هر دو حساب در
سناریوی ارائه قابل آزمون باشد. نقش `SYSTEM_ADMINISTRATOR` به‌تنهایی هیچ
Permission گزارش دریافت نمی‌کند.

در پایان تراکنش، وجود دقیق ۱۲ پرسونای تعریف‌شده، پوشش تمام نقش‌ها، یکتایی شناسه‌های ورود و
اثر انگشت کامل رکوردهای ساخته‌شده کنترل می‌شود. هر مغایرت یا نقص در داده canonical باعث
rollback کل تراکنش خواهد شد.
