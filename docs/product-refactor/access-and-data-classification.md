## طبقه‌بندی پیشنهادی داده

| سطح | نمونه | قاعده |
| --- | --- | --- |
| PUBLIC | مقاله دانش عمومی تأییدشده | بدون Login فقط در صورت تصویب D-020 |
| INTERNAL | نام صف، Rule غیرحساس، یادداشت عملیاتی عمومی | فقط کارکنان مجاز |
| CONFIDENTIAL | متن تیکت، فایل، قرارداد مرتبط، داده شرکت | فقط Party و تیم/Scope مجاز |
| RESTRICTED | کدملی، موبایل، حساب بانکی، مبلغ/پرداخت، امضا، نمایندگی | حداقل دسترسی، Masking و Audit مشاهده |
| HIGHLY_RESTRICTED | شواهد حقوقی ویژه، رخداد امنیتی، اطلاعات احراز هویت حساس | Approval یا Break-glass زمان‌دار |

## کنترل‌های لازم

- مجوز در Query و Service Layer اعمال شود؛ مخفی‌کردن دکمه کافی نیست.
- Resource خارج Scope با 404 پنهان شود، مگر پاسخ استاندارد امنیتی دیگری تصویب شود.
- Party/Organization Scope از ورودی Client پذیرفته نشود و در سرور بازسازی شود.
- فیلدهای حساس در Log، Metrics، Error و Search Index وارد نشوند.
- Break-glass نیازمند دلیل، زمان انقضا، اعلان امنیتی و Audit است.
- Download فایل باید مجوز Ticket و Message والد را دوباره بررسی کند.
- Internal Note و Draft پاسخ AI در DTO کاربر وجود نداشته باشند.
- Export و گزارش شرکت باید همان Scope API عادی را رعایت کند.

## تغییرات حساس پیشنهادی

- افزودن/حذف نماینده شرکت
- تغییر Scope نماینده
- تغییر شماره حساب یا مقصد پرداخت
- تغییر اطلاعات قراردادی یا امضاکننده مجاز
- انتقال مالکیت دارایی یا نیروگاه
- مشاهده یا Export داده Highly Restricted

هر مورد باید Request، Approver، Decision، Reason، Before/After و Timestamp مستقل داشته باشد.
